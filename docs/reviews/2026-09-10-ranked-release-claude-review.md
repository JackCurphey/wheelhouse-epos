# Adversarial review of the Release 1 implementation plan — 10 September 2026

Reviewer: Claude Fable 5.1 (low-effort run, no tools). Evidence: the plan, the earlier adversarial review, the traceability CSV, the review prompt, the 8 September review and prototype decisions, the pinned competitive trials, and the supplied code excerpts. No tests were run, no code was executed, no provider or device was exercised. Findings marked **Confirmed** were read in the supplied material; **Inference** means a plausible failure that needs a test.

## Verdict

**Ready for detailed issue splitting with the corrections below applied; the plan itself remains a draft until the master-plan amendment is recorded.** Analysis, issue preparation and bounded access probes may proceed. This review does not authorise any implementation that depends on an open decision, and calling snapshot or approval work "internal" does not remove the D02 gate. The plan covers all 172 selected rows, keeps the 102 Later and 43 No rows intact, and has an acyclic dependency graph. The real blockers to *implementation* are not planning defects but three product decisions (D02 version-bound approval, D04 deposit bucket conflict, D07 first POS series) and external access for R-Series, WhatsApp and printing. The planning defects found were: several hard dependencies that were really soft, one group decision (D08) accidentally gating all staff-access and job-model work, a capacity model gap visible in current code that the plan did not name, and a few status/acceptance statements that were imprecise or unverifiable from evidence.

## First five implementation issue drafts (not published)

These are a dependency sequence, not five tasks that all start together. I-01 and I-02 have no prerequisite. I-03 and I-04a wait for I-01. I-04b waits for decision D02. I-05 waits for I-03 and I-04a. None is authorised for implementation by this review; issue preparation may proceed now; implementation follows the recorded master-plan amendment.

**I-01 Tenant integrity audit and fix (W01a).** Prerequisite: none. Actor: platform engineer. Command: run a two-shop fixture, attempt every cross-shop foreign ID via raw HTTP and direct SQL under the application role. Acceptance: every cross-tenant read, write and relation fails; migration applies on a populated fixture; no permission depends on UI hiding. Failure case: a job referencing another shop's bike is accepted. Exclusions: group model.

**I-02 Durable session revocation (W02).** Prerequisite: none. Command: deactivate a team member while their session is live, then reactivate. Acceptance: old token rejected immediately and still rejected after reactivation; new login required; actor history preserved; stale comments in `customer-auth.js` corrected. Failure case: old token resumes after reactivation (current behaviour).

**I-03 Job without order, with job-owned planned effort (W03).** Prerequisite: I-01 merged. Command: create a job with `skipAutoOrder` and planned minutes; restart; read it back. Acceptance: job persists with duration and no sale document; existing jobs backfilled; version column present; stale edit returns conflict with no partial change. Failure case: job with no order loses its duration or is invisible on the diary. Exclusions: eleven statuses, custody.

**I-04a Amount and tax calculation with labour-stock regression (W04).** Prerequisite: I-01. No decision needed. Command: add a labour line and a product line with inclusive, exclusive and discounted prices; re-read totals. Acceptance: inclusive/exclusive/discount rounding fixtures reconcile; stored tax facts replace the hardcoded rate; labour line never decrements or restocks physical stock (#17 reproduced then fixed). Failure case: labour line restocks a product.

**I-04b Proposal and booking snapshot semantics (W04).** Prerequisite: I-04a and decision D02 recorded. Command: change the catalogue price and tax setting after a proposal exists; re-read the proposal. Acceptance: agreed lines unchanged according to the D02 answer on version-bound approval. Flag: overlaps Later 208 and No 169; the snapshot semantics are disputed and stay gated on D02. This is not implemented as an "internal" feature ahead of that decision.

**I-05 Atomic reservation including untimed jobs (W05).** Prerequisite: I-03, I-04a; D06 for drop-off policy and D09 for cancellation/override semantics. Command: two concurrent HTTP requests from separate sessions for the last slot; then two concurrent untimed drop-off requests on a day with one job of effort remaining. Acceptance: exactly one acceptance in each case; failed reschedule preserves the original hold; expiry releases capacity once; staff reserve override still allowed. Failure case: a timed booking succeeds on a day already filled by an untimed staff job (confirmed code shape, not reproduced), or both untimed requests succeed once drop-off booking exists (hypothetical; public drop-off booking is not accepted today).
